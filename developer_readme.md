```bash
git clone --recurse-submodules https://github.com/coenarrow/remote-physiology.git
# already cloned without it:
git submodule update --init --recursive
# so the preprocessor submodule sits on main and can be committed from:
git submodule foreach 'git checkout main'
git config push.recurseSubmodules check
```

`#uv sync` is the whole install on Linux, macOS and **Windows** — no conda, no
WSL. `pyproject.toml` + `uv.lock` are the single source of truth for
dependencies; add packages with `uv add`, never pip.

`uv sync` does **not** need the submodule — training works fine in a
non-recursive clone. Only cache-building does. The preprocessor at
`dataset/cachers/neckflix` is deliberately outside this project's dependency graph: a
path source would make `uv lock` fail wherever the submodule was skipped, and
keeping the envs apart keeps `av` / `opencv-python-headless` / `hdf5plugin`
and its `zarr>=3.3,<4` cap out of the training environment. Build a cache with
`uv run --project dataset/cachers/neckflix neckflix-preprocess ...`, which resolves
from that repo's own `uv.lock` — the same lock its published GHCR image builds
from — and its own Python 3.12.

Windows needs the CUDA toolkit (>= 11.6) and MSVC build tools on the machine,
because `mamba-ssm` and `causal-conv1d` publish no Windows wheels and so compile
from source; budget half an hour for the first sync, after which uv caches the
result. `mamba-ssm` additionally does not compile with MSVC as published, so
Windows builds [`vendor/mamba-ssm`](vendor/mamba-ssm) — the same upstream
2.3.2.post1 release with three mechanical fixes, regenerated by
[`tools/vendor_mamba_windows.py`](tools/vendor_mamba_windows.py), which explains
each one. Linux and macOS keep the published packages. Of that release's
Mamba3, Windows has the SISO layer (pure Triton); `Mamba3(is_mimo=True)` and
single-token decoding need TileLang and the CuTe DSL, which install on Linux
only.

Into a **fresh** environment, install in two steps — `mamba-ssm` and
`causal-conv1d` build against the project's own torch rather than an isolated
one, so torch has to be there before they are built:

```bash
uv sync --no-install-package mamba-ssm --no-install-package causal-conv1d
uv sync
```

**After every torch bump, force `causal-conv1d` to rebuild.** uv caches the
built wheel by its sdist, not by the torch it was linked against, so a sync
after the bump reinstalls the old binary and `import causal_conv1d` fails with
`DLL load failed ... The specified procedure could not be found`. `mamba_ssm`
swallows that error: Mamba1 silently drops to `nn.Conv1d`, and Mamba2's fused
path dies with `'NoneType' object is not callable`. If `import
selective_scan_cuda` fails the same way, do the same for `mamba-ssm`.

```bash
uv cache clean causal-conv1d
uv sync --reinstall-package causal-conv1d
```

**Build from a 64-bit compiler shell.** Left to itself, setuptools activates
the 32-bit-hosted `cl.exe` (`HostX86\x64`), which is capped at ~4 GB and can
die on `causal-conv1d`'s largest kernel with `fatal error C1060: compiler is
out of heap space` however much RAM the machine has. Run the sync commands
above from the *x64 Native Tools Command Prompt for VS 2022* (or after calling
`vcvars64.bat`) with these set, which makes setuptools use that shell's 64-bit
`cl.exe` (6 minutes here, against 20 for the 32-bit one):

```bat
set DISTUTILS_USE_SDK=1
set MSSdk=1
```

Without `mamba-ssm` (no CUDA, or an unsupported platform), PhysMamba still
runs: `MambaRef` (`neural_methods/model/physmamba/mamba_ref.py`) is a pure-PyTorch selective-SSM block that trains
and is parameter-compatible with the real one. A correctness path, not a speed
one.
